# 1\. Requirements Interpretation

## 1.1 Accounts

### Req-1: Account Creation and Metadata

The system must allow users to create multiple financial accounts.

**Account Attributes**

Every account must have:

- A unique system-generated identifier.
- A user-defined account name.
- An account type.
- A creation timestamp.
- An account status.

**Supported Account Types**

- BANK
- SAVINGS
- CASH
- MOBILE

**Validation and Business Rules**

- Every newly created account must have an initial status of ACTIVE.
- Account identifiers and creation timestamps must be generated internally by the application.
- Account names must not be empty.
- Account names must contain at least four characters.
- No maximum account-name length is imposed.
- Account names must be unique across existing accounts, regardless of account status.
- Account-name uniqueness comparisons must be case-insensitive.
- Account identifiers must be unique within the application.

### Req-2: Account Retrieval and Inspection

The system must provide mechanisms for retrieving and inspecting financial accounts.

**Retrieval Operations**

- Retrieve all active accounts through the default account listing.
- Retrieve inactive accounts through a separate retrieval mechanism.
- Retrieve individual accounts using their unique identifiers.

**Account Inspection**

Account retrieval must provide:

- Account metadata.
- Current ledger-derived balance.

The system must support the following account inspection operations:

- Balance inquiries.
- Deposit recording.
- Withdrawal recording.
- Account deactivation.

**Business Rules**

- Account balances must be calculated by the Business Logic Layer using effective transaction history.

### Req-3: Account Activation and Deactivation

The system must allow users to deactivate active accounts and reactivate inactive accounts.

**Deactivation Rules**

- Only active accounts may be deactivated.
- Deactivation must change the account status to INACTIVE.
- Deactivated accounts must be excluded from the default active-account listing.
- Deactivation must only be permitted when the account's calculated balance is exactly zero Kobo.

**Reactivation Rules**

- The system must allow users to reactivate inactive accounts.
- Reactivation must change the account status to ACTIVE.
- Reactivation must verify that the account exists and is currently eligible for reactivation.
- Reactivation must perform an account-name uniqueness check against all other existing accounts, regardless of account status.
- Reactivation must not modify historical transactions or financial balances.

**General Rules**

- Accounts involved in financial operations must satisfy the applicable active-status requirements.

## 1.2 Income Recording

### Req-4: Income Recording and Metadata

The system must allow users to record income transactions against existing financial accounts.

Income transactions must be classified as DEPOSIT.

**Transaction Attributes**

Every deposit transaction must capture:

- A unique transaction identifier generated by the Business Logic Layer.
- A positive transaction amount represented in integer Kobo.
- The target account identifier.
- The transaction date in YYYY-MM-DD format.
- An optional transaction description.

**Validation Rules**

- Transaction amounts must be positive monetary values.
- Monetary input must support up to two decimal places.
- Monetary amounts must be converted into integer Kobo before processing.
- Transaction dates must represent valid calendar dates.
- Transaction dates must not be in the future.
- Deposits must only be permitted into active accounts.

### Req-5: Income Ledger Recording

Every successfully recorded deposit must:

- Be added to the centralized transaction history.
- Reference its target account.
- Persist its transaction record and associated financial effect together.

**Persistence Rules**

- The application must persist proposed state before updating its active in-memory state.
- Failed persistence operations must not commit proposed application state in memory.

## 1.3 Expense Recording

### Req-6: Expense Recording and Metadata

The system must allow users to record expenses against existing financial accounts.

Expense transactions must be classified as WITHDRAW.

**Transaction Attributes**

Every withdrawal transaction must capture:

- A unique transaction identifier generated by the Business Logic Layer.
- A positive transaction amount represented in integer Kobo.
- The source account identifier.
- The transaction date in YYYY-MM-DD format.
- An expense category.
- An optional transaction description.

**Supported Expense Categories**

- FOOD
- BILLS
- TRANSPORT
- AIRTIME
- HEALTH
- SHOPPING
- ENTERTAINMENT
- OTHERS

**Validation Rules**

- Expense categories must be selected from a centrally defined expense-category enumeration.
- Withdrawals must only be permitted from active accounts.

### Req-7: Expense Financial Validation and Ledger Recording

The system must enforce financial integrity when recording expenses.

**Financial Validation**

- The system must prevent transactions that would produce a negative historical account balance.
- The Business Logic Layer must validate financial sufficiency before committing an expense.

**Ledger Recording**

- Every successfully recorded withdrawal must be added to the permanent transaction history.
- Every withdrawal must reference its source account.
- The transaction and its corresponding financial effect must be persisted together.

## 1.4 Internal Transfers

### Req-8: Transfer Recording and Metadata

The system must allow users to transfer funds between their own financial accounts.

**Transaction Attributes**

Every transfer transaction must capture:

- A unique transaction identifier generated by the Business Logic Layer.
- A source account identifier.
- A target account identifier.
- A positive transaction amount represented in integer Kobo.
- A transaction date in YYYY-MM-DD format.

**Validation Rules**

- Both accounts must exist.
- Both accounts must have ACTIVE status.
- The source and target accounts must be distinct.
- Transfer transactions must be classified as TRANSFER.

### Req-9: Transfer Financial Validation

The Business Logic Layer must validate the financial implications of every proposed transfer.

**Financial Validation**

- The source account must have sufficient funds.
- Transfers must not produce negative historical account balances.

**Financial Effects**

A successful transfer must:

- Reduce the source account's calculated balance by the transfer amount.
- Increase the target account's calculated balance by the same amount.
- Preserve the combined financial value across both accounts.

**Transaction Integrity**

- Both account references must be retained in the transaction record.
- Transfer transactions must not contain expense categories.

### Req-10: Transfer Ledger Recording

Every successful transfer must:

- Be recorded in the permanent transaction history.
- Retain both source and target account references.
- Have its transaction record and associated financial effects persisted together.

**State Management**

- The application must only update its in-memory state after successful persistence.

## 1.5 Transaction History

### Req-11: Comprehensive Transaction Ledger

The system must maintain a centralized historical transaction ledger.

**Transaction Attributes**

Every transaction must contain:

- A unique transaction identifier.
- A positive integer amount represented in Kobo.
- A transaction date.
- A transaction classification.
- Relevant account references.
- An optional transaction description.
- An optional expense category.
- An optional reference to an original transaction for reversal records.

**Supported Transaction Classifications**

- TRANSFER
- WITHDRAW
- DEPOSIT
- REVERSAL

**Transaction Rules**

- Expense categories must only be associated with WITHDRAW transactions.
- Transaction descriptions are optional.
- Transaction identifiers must be unique within the transaction history.
- Historical transactions must remain accessible regardless of the status of their associated accounts.
- The system must provide a centralized view of the complete transaction history.

### Req-12: Transaction Immutability

Transaction records must be immutable after creation.

**Immutability Rules**

- Existing transactions must not be directly modified through normal application operations.
- Existing transactions must not be directly deleted through normal application operations.
- Corrections must be performed through compensating reversal transactions.
- Original transaction records must remain unchanged and accessible after reversal.

### Req-13: Transaction History Pagination

The system must implement application-level pagination when retrieving transaction history.

**Pagination Rules**

- The default page size must be 25 transactions.
- Users must be able to navigate between available transaction history pages through the CLI.
- Transactions must be sorted in reverse-chronological order by default.
- Pagination must be applied after filtering and sorting operations.
- The system must handle empty pages gracefully.
- Invalid page selections must be handled gracefully.

## 1.6 Transaction Search and Filtering

### Req-14: Transaction Search

The system must allow users to search historical transactions using supported transaction attributes.

**Search Rules**

- Search results must be retrieved from the centralized transaction ledger.
- Searching must not modify existing transaction records.
- Search operations must support relevant transaction attributes.
- Search results must be compatible with transaction filtering and pagination.

### Req-15: Compound Transaction Filtering

The system must support combining multiple filtering criteria within a single transaction history request.

**Supported Filtering Criteria**

1. **Temporal Filtering**
   - Specific transaction dates.
   - Inclusive transaction date ranges.
2. **Categorical Filtering**
   - Transaction classification.
   - Expense category.
3. **Entity-Based Filtering**
   - Associated account identifiers.
4. **Quantitative Filtering**
   - Inclusive minimum transaction amounts.
   - Inclusive maximum transaction amounts.

**Filtering Rules**

- Multiple active filters must be evaluated using logical AND conditions.
- Account-based filtering must consider both source and target account references where applicable.
- Reversal records must be identifiable through their transaction classification and original transaction references.
- Filtering must not modify historical transaction records.

### Req-16: Empty Search Results

When a search or filter produces no matching transactions:

- The Business Logic Layer must return an empty collection.
- The presentation layer must display a clear notification indicating that no matching transactions were found.
- Users must be able to reset active filters.
- Users must be able to return to the unfiltered transaction history.

## 1.7 Account Balances and Aggregate Net Worth

### Req-17: Ledger-Derived Account Balances

The system must calculate individual account balances from effective transaction history.

**Balance Calculation Rules**

- Account balances must not be maintained as independently mutable financial values.
- The Business Logic Layer must calculate balances using effective transactions.
- Balance calculations must use integer Kobo.

**Financial Effects**

| Transaction Type | Financial Effect |
| --- | --- |
| DEPOSIT | Increases the target account balance. |
| WITHDRAW | Decreases the source account balance. |
| TRANSFER | Decreases the source account balance and increases the target account balance. |
| REVERSAL | Cancels the financial effect of the referenced original transaction. |

**Reversal Rules**

- Reversed transactions must not contribute to effective balance calculations.
- Reversal records must be excluded from effective balance calculations together with their corresponding original transactions.

The calculated balance must represent the net financial effect of effective transaction history.

### Req-18: Aggregate Net Worth Dashboard

The system must provide a consolidated dashboard displaying the aggregate balance across all active accounts.

**Calculation Rules**

- Aggregate net worth must be calculated as the sum of the ledger-derived balances of all active accounts.
- Inactive accounts must be excluded from aggregate net-worth calculations.
- The dashboard must reflect successful financial operations automatically.
- The dashboard must use the same balance calculation mechanism as individual account inquiries.

### Req-19: Mathematical Balance Integrity

The system must guarantee that aggregate net worth equals the sum of all individual active account balances.

**Consistency Requirements**

- Account listings must display ledger-derived balances.
- Individual account inspections must display ledger-derived balances.
- The aggregate net-worth dashboard must display the sum of active account balances.
- Financial calculations must use integer Kobo to avoid floating-point precision errors.
- Transfers must preserve aggregate net worth.
- Reversals must correctly restore the financial effect of reversed transactions.

## 1.8 Financial Reports

### Req-20: Date-Bounded Financial Reporting

The system must allow users to generate financial reports for a specified reporting period.

**Reporting Inputs**

Users must provide:

- A start date.
- An end date.

**Validation Rules**

- Both dates must be valid calendar dates.
- Both dates must be inclusive.
- The start date must not be later than the end date.
- Transaction dates must be validated before report generation.

Only transactions falling within the selected reporting period must contribute to period-based reporting metrics.

### Req-21: Core Financial Reporting Metrics

For the selected reporting period, the system must calculate the following metrics:

**Total Income**

The sum of effective DEPOSIT transactions.

**Total Expenses**

The sum of effective WITHDRAW transactions.

**Net Delta**

Total Income minus Total Expenses.

**Reporting Rules**

- TRANSFER transactions must be excluded from total income and total expense calculations.
- Reversed original transactions must be excluded from effective income and expense calculations.
- Corresponding reversal records must not independently inflate or reduce ordinary income and expense totals.

### Req-22: Expense Category Breakdown

The system must provide a breakdown of effective expenses grouped by expense category.

**Reporting Rules**

- Only effective WITHDRAW transactions must contribute to expense-category totals.
- Expense amounts must be aggregated by their corresponding categories.
- Category totals must be restricted to the selected reporting period.
- The reporting output must present calculated category totals to the user.

### Req-23: Per-Account Financial Activity Reports

The system must provide financial activity reports for individual accounts.

Reports must identify incoming and outgoing financial movements within the selected reporting period.

**Supported Financial Activities**

- Deposits.
- Withdrawals.
- Transfers.
- Reversal movements.

**Reporting Rules**

- The report must distinguish between incoming and outgoing movements.
- Deposits must be represented as incoming movements.
- Withdrawals must be represented as outgoing movements.
- Transfers must be represented as outgoing movements for source accounts.
- Transfers must be represented as incoming movements for target accounts.
- Reversal movements must be represented according to their corresponding financial effects.
- Original transactions that have been reversed must not contribute to effective financial activity totals.
- Account-level reports must preserve the distinction between ordinary income, expenses, transfers, and reversals.

### Req-24: Transfer and Reversal Reporting Rules

The system must maintain accurate financial reporting when transfers and reversals are involved.

**Transfer Reporting**

- TRANSFER transactions must not artificially inflate or reduce ordinary income and expense totals.

**Reversal Reporting**

- Reversal records must not independently inflate or reduce ordinary income and expense reporting totals.
- Reversed original transactions must be excluded from effective income and expense reporting.
- Account-level financial activity reports must reflect the appropriate movements resulting from effective transactions.
- Reversal relationships must be considered when determining effective financial activity.

## 1.9 Transaction Correction and Reversal

### Req-25: Transaction Reversal

The system must provide a mechanism for reversing incorrectly recorded transactions without directly modifying or deleting historical records.

**Reversal Attributes**

Every reversal must:

- Be recorded as a separate transaction classified as REVERSAL.
- Reference the unique identifier of its original transaction.
- Retain the original transaction's amount.
- Retain the original transaction's relevant account references.
- Have its own unique transaction identifier.
- Have its own transaction date.

**Reversal Eligibility Rules**

- A transaction may only be reversed once.
- A reversal transaction must not itself be eligible for reversal.
- The original transaction must remain unchanged and accessible in the historical transaction ledger.
- Accounts associated with the original transaction must exist and have ACTIVE status when the reversal is processed.

### Req-26: Reversal Financial Integrity

The Business Logic Layer must validate reversal relationships before committing a reversal.

**Validation Requirements**

The system must ensure that:

- The original transaction exists.
- The original transaction is eligible for reversal.
- The original transaction has not already been reversed.
- The reversal references the correct original transaction.
- The reversal amount matches the original transaction amount.
- The reversal account references match the original transaction's account references.
- A reversal cannot reference another reversal transaction.

**Financial Integrity Rules**

- The effective transaction calculation must exclude both the original transaction and its corresponding reversal.
- The combined financial effect of a successfully reversed transaction and its reversal must be zero.
- Reversal creation must be persisted together with the updated transaction history.
- The original and reversal records must remain independently identifiable in the historical ledger.

## 1.10 Data Persistence and Recovery

### Req-27: JSON-Based Data Persistence

The system must persist application data in a JSON file.

**Persisted Data Structure**

Persisted application data must contain:

- An accounts collection.
- A transactions collection.

**Serialization Requirements**

- Account serialization must be delegated to the Account domain model.
- Transaction serialization must be delegated to the Transaction domain model.
- Account records must include their identifier, name, type, status, and creation timestamp.
- Account status must be serialized using the JSON field `acc_status`.
- Transaction records must preserve all fields required for complete reconstruction of transaction history.

### Req-28: Atomic Data Persistence

The system must use a temporary staging file when saving application data.

**Persistence Procedure**

1. Serialize the proposed application state.
2. Write the serialized data to a temporary staging file.
3. Flush and synchronize written file contents.
4. Replace the existing data file using an atomic file-replacement operation.
5. Commit the proposed in-memory state only after successful persistence.

**Failure Handling**

- Incomplete temporary files must be removed following unsuccessful save operations.
- Failed persistence operations must leave the previously committed in-memory state unchanged.

### Req-29: Data Loading and Integrity Validation

The system must reconstruct persisted account and transaction records through their respective domain-model deserialization methods.

**Loading Rules**

- A missing data file must be treated as a new application installation.
- A new installation must initialize empty account and transaction collections.
- Invalid JSON structures must be treated as corrupted persisted data.
- Missing or invalid required entity attributes must be treated as corrupted persisted data.
- Invalid or missing persisted account statuses must raise `StorageCorruptedError`.
- Account identifiers stored as JSON object keys must match their corresponding reconstructed account identifiers.

**Post-Loading Business Validation**

The Business Logic Layer must validate:

- Transaction identifier uniqueness.
- Reversal relationships.
- Account references.
- Chronological financial consistency.
- Historical account balance validity.

Persisted data that fails entity reconstruction or business validation must raise `StorageCorruptedError`.

# 2\. Business Rules

## 2.1 Accounts & Lifecycle Management

### BR-01: Structural Integrity (Naming Constraints)

- Account names must not be empty, null, or consist exclusively of whitespace.
- Leading and trailing whitespace must be removed before validation and persistence.
- Account names must contain at least four characters.
- No maximum account-name length is imposed by the application.
- Account names must be unique across existing accounts.
- Uniqueness evaluation must be case-insensitive.
- Duplicate names must be rejected with an appropriate `DuplicateAccountNameError`.
- Account creation must perform uniqueness validation against existing accounts.

### BR-02: Initial State and Typology

- Every newly created account must automatically receive a unique system-generated identifier.
- Account identifiers must follow the application's identifier-generation convention.
- Account identifiers must use the `acc_` prefix followed by a randomly generated alphanumeric suffix.
- Every new account must have an initial status of ACTIVE.
- Every new account must have an initial balance of zero Kobo.
- Account IDs, timestamps, statuses, and initial balances must be assigned internally.
- Account types must strictly map to the following supported classifications:
  - BANK
  - CASH
  - SAVINGS
  - MOBILE
- Any unsupported account type must be rejected.
- Initial funding must be recorded through a valid DEPOSIT transaction rather than directly assigning a starting balance.

### BR-03: Reference Validation

- The system must reject transactions referencing non-existent account IDs.
- Account references must be validated against the application's loaded account collection.
- Account names must not be treated as substitutes for unique account identifiers during transaction processing.
- Invalid account references must produce appropriate domain errors.

### BR-04: Active List Isolation

- The standard account directory must exclusively display accounts with ACTIVE status.
- Inactive accounts must remain accessible through a dedicated inactive-account directory.
- Users must be able to inspect active accounts and access their available account operations.
- Inactive accounts must retain their historical balances and transaction associations.
- Account retrieval must not modify the account's status or historical financial records.

### BR-05: Deactivation and Reactivation Isolation

- An account may transition from ACTIVE to INACTIVE only if its ledger-derived balance is exactly zero Kobo.
- The ledger-derived balance must serve as the authoritative value for deactivation validation.
- An inactive account must be prevented from participating in new financial transactions.
- This restriction applies to DEPOSIT, WITHDRAW, and TRANSFER operations.
- Inactive accounts must not participate in transfers as either source or target accounts.
- Reactivation must only be performed on an account with INACTIVE status.
- Reactivation must change the account status to ACTIVE without modifying its historical transactions or balance.
- Reactivation must not generate a new account identifier.
- Account deactivation and reactivation must be persisted through the established atomic file replacement mechanism.

## 2.2 Monetary Values and Validation Mechanics

### BR-06.1: Monetary Representation and Precision Integrity

- All monetary values must be internally represented and stored as integers in the smallest currency denomination, Kobo.
- One Nigerian Naira equals 100 Kobo.
- During input processing, valid Naira amounts must be converted into Kobo by multiplying the decimal amount by 100.
- All financial calculations, including account balances, transfers, reversals, and financial aggregations, must operate exclusively on integer Kobo values.
- During data presentation, Kobo values must be converted into Naira and formatted to exactly two decimal places.
- Binary floating-point arithmetic must not be used throughout monetary processing.
- Monetary values must never be stored as floating-point numbers in JSON.

### BR-06.2: Decimal-to-Integer-Kobo Input Conversion Mechanism

- The application must receive monetary input as strings from the CLI.
- Monetary input must be validated using Python's `decimal.Decimal` type.
- Before conversion, the application must validate that the input:
  - Is a valid numeric monetary representation.
  - Is finite.
  - Is strictly greater than zero.
  - Contains no more than two decimal places.
  - Does not exceed the transaction ceiling established in BR-09.
- Monetary input must not contain unsupported characters or formatting.
- Following successful validation, the Decimal amount must be multiplied by 100.
- The resulting value must be converted into an integer representing Kobo.
- The integer Kobo value must be used for all subsequent financial calculations, storage, balance validation, transfers, and reversals.
- Invalid monetary input must raise `InvalidAmountError`.

**Illustrative conversion example:**

| User Input (Naira) | Decimal Calculation | Stored Value (Kobo) |
| --- | --- | --- |
| ₦100 | 100 × 100 | 10,000 |
| ₦250.50 | 250.50 × 100 | 25,050 |
| ₦1,250.75 | 1250.75 × 100 | 125,075 |
| ₦0.01 | 0.01 × 100 | 1 |

### BR-07: Data Type and Range Constraints

- Transaction amounts must be valid positive monetary values.
- Empty strings, null values, and invalid monetary representations must be rejected.
- Transaction amounts must be strictly greater than zero.
- Zero and negative monetary values must be rejected during ordinary transaction creation.
- Currency symbols, commas, and unsupported formatting characters must be rejected.
- Reversal transaction amounts must be positive and must exactly match their original transaction amounts.
- Invalid monetary values must raise `InvalidAmountError`.

### BR-08: Numeric Precision and Scale (Currency Guard)

- The system must accept monetary input containing zero, one, or two decimal places.
- Inputs containing more than two decimal places must be rejected.
- The system must not silently round or truncate invalid monetary input.
- All validated monetary amounts must be converted into integer Kobo before financial calculations begin.
- Python's Decimal implementation must be used during monetary input conversion.
- Binary floating-point types must not be used during monetary processing.

### BR-09: Transaction Ceiling (Business Validation Boundary)

- The system must reject any single transaction exceeding ₦99,999,999.99.
- The maximum corresponding stored transaction amount is 9,999,999,999 Kobo.
- The ceiling must be enforced before any financial transaction is committed.
- The ceiling applies to DEPOSIT, WITHDRAW, TRANSFER, and REVERSAL transactions.
- The ceiling applies to individual transactions rather than cumulative account balances or aggregate ledger values.
- Account balances and aggregate financial totals may exceed the individual transaction ceiling through multiple valid transactions.

### BR-10: Balance Sufficiency (Overdraft Prevention)

- For WITHDRAW and TRANSFER operations, the system must verify that the designated source account has sufficient ledger-derived funds.
- The source account's balance must be greater than or equal to the intended transaction amount.
- If the transaction amount exceeds the available balance:
  - The operation must be aborted.
  - No transaction record must be appended.
  - No in-memory application state must be modified.
  - No persistence operation must be performed.
  - An `InsufficientFundsError` must be raised.

### BR-11: Financial State Authority and Balance Consistency

- The transaction ledger must serve as the authoritative source of financial truth for all account balances.
- Account balances must be calculated from the cumulative financial effects of historical transactions.
- The application must not rely on independently maintained or manually assigned account balances.
- Every successful DEPOSIT, WITHDRAW, TRANSFER, or REVERSAL operation must update the effective financial state through the corresponding ledger record.
- Financial transaction records must be persisted before the proposed in-memory application state is committed.
- If persistence fails, the existing in-memory application state must remain unchanged.
- Ledger-derived balances must remain mathematically consistent with the cumulative financial effects of historical transactions.

### BR-11.1: Ledger-Derived Balance Calculation

The system must calculate each account's authoritative balance using the cumulative financial effects of its associated transaction history.

The calculation must follow these rules:

- **DEPOSIT:** Add the transaction amount to the target account.
- **WITHDRAW:** Subtract the transaction amount from the source account.
- **TRANSFER:** Subtract the transaction amount from the source account and add the same amount to the target account.
- **REVERSAL:** Cancel the financial effect of the original transaction.

Reversal calculations must follow the original transaction classification:

- **Reversal of DEPOSIT:** Subtract the original deposit amount from the original target account.
- **Reversal of WITHDRAW:** Add the original withdrawal amount back to the original source account.
- **Reversal of TRANSFER:** Add the original transfer amount back to the original source account and subtract the same amount from the original target account.

Additional rules:

- Newly created accounts must begin with a balance of zero Kobo.
- Initial funding must be recorded through a valid DEPOSIT transaction.
- Inactive accounts must retain their historical balances and transaction associations.
- The calculated balance must serve as the authoritative reference during overdraft validation and account lifecycle validation.
- Reversal financial effects must be derived from the original transaction's account references and amount.
- A successfully reversed transaction and its corresponding reversal must have a combined financial effect of zero.

### BR-12: Effective Transaction History

- The application must maintain a complete historical transaction collection.
- Historical transaction records must not be directly modified or deleted through normal application operations.
- The system must distinguish between historical transactions and effective financial transactions.
- Effective transactions must exclude REVERSAL records and original transactions that have been reversed.
- Original transactions that have been reversed must remain available in the historical transaction collection.
- REVERSAL records must remain independently identifiable in the historical transaction collection.
- Effective transaction history must be used for ordinary financial reporting.
- Ledger-derived balance calculations must account for the cancellation of reversed original transactions.
- Transaction reversal must not remove historical records.

## 2.3 Transfer Mechanics

### BR-13: Self-Transfer Prevention

- The system must reject transfer operations where the source account identifier matches the target account identifier.
- Validation must be based on account IDs rather than account names.
- Source and target accounts must represent distinct financial accounts.

### BR-14: Multi-Account Lifecycle and Existence Check

- The system must verify the existence of both source and target accounts before executing a transfer.
- The operation must fail if either account ID does not exist in the loaded application state.
- The system must block transfers if either account has INACTIVE status.
- Both accounts must be ACTIVE before the transfer can proceed.

### BR-15: Transfer Quantification and Global Constraints

- All transfer amounts must comply with BR-06, BR-07, BR-08, and BR-09.
- Transfer amounts must be stored as integer Kobo.
- The same transaction amount must be debited from the source account and credited to the target account.
- TRANSFER transactions must contain both source and target account references.
- TRANSFER transactions must not contain an expense category.
- Transfers must be recorded as a single transaction rather than separate withdrawal and deposit records.

### BR-16: Asset Sufficiency (Overdraft Enforcement)

- The system must confirm that the source account's ledger-derived balance is greater than or equal to the transfer amount.
- If the source account has insufficient funds:
  - The transaction must be aborted.
  - No application state must be committed.
  - No transaction must be appended.
  - An explicit `InsufficientFundsError` must be raised.

## 2.4 Date Validation

### BR-17: Date Format and Structural Integrity

- The system must accept transaction dates exclusively in the `YYYY-MM-DD` format.
- The CLI must not require users to provide hours, minutes, seconds, timezone offsets, or timezone indicators.
- The system must validate the exact input structure before attempting date conversion.
- Invalid date formats must raise `InvalidDateError`.

### BR-18: Calendar Consistency Checks

- The system must perform real-calendar validation on all transaction date inputs.
- Non-existent calendar dates, such as `2026-02-30` or `2026-11-31`, must be rejected.
- Calendar validation must ensure that the supplied year, month, and day represent a valid calendar date.
- Invalid calendar dates must raise `InvalidDateError`.

### BR-19: Future-Date Restriction

- The system must compare each validated transaction date against the current calendar date.
- Any transaction dated later than the current calendar date must be rejected.
- Transactions dated on the current date or any previous valid calendar date must be accepted.
- Date comparisons must use calendar dates rather than timezone-aware timestamps.
- Future-dated transactions must raise `InvalidDateError`.

## 2.5 Expense Category Rules

### BR-20: Centralized Expense Category Definition

- The application must maintain one centrally defined collection of permitted expense categories.
- The collection must be maintained in `models/enums.py` through the `ExpCatOpts` enumeration.
- The supported expense categories are:
  - FOOD
  - BILLS
  - TRANSPORT
  - AIRTIME
  - HEALTH
  - SHOPPING
  - ENTERTAINMENT
  - OTHERS
- The collection must be treated as application-controlled configuration.
- The presentation layer must obtain available expense categories from the centrally defined enumeration.
- WITHDRAW transactions representing expenses must contain a valid category from the configured collection.
- DEPOSIT and TRANSFER transactions must not independently introduce expense categories.
- Invalid expense categories must be rejected before the transaction is committed.

## 2.6 Transaction Reversal Rules

### BR-21: Reversal Eligibility and Reference Integrity

- Only existing DEPOSIT, WITHDRAW, and TRANSFER transactions may be reversed.
- A REVERSAL transaction must reference exactly one original transaction through `reverses_transaction_id`.
- The referenced transaction must exist in the historical ledger.
- A transaction that has already been reversed must not be reversed again.
- A REVERSAL transaction must not reference another REVERSAL transaction.
- The original transaction and its associated metadata must remain unchanged.
- Reversal operations must validate the existence and active status of all accounts affected by the original transaction.

### BR-22: Reversal Financial Effects

- A reversal must exactly negate the financial effect of its original transaction.
- Reversing a DEPOSIT transaction must debit its original target account.
- Reversing a WITHDRAW transaction must credit its original source account.
- Reversing a TRANSFER transaction must credit the original source account and debit the original target account.
- Both accounts involved in a transfer reversal must be updated as one atomic logical operation.
- The reversal must use the original transaction's amount and account references.
- The system must validate the resulting proposed financial state before persistence.
- A reversal must not be permitted if it would produce a negative historical account balance.
- If a reversal cannot be completed, the original transaction and existing application state must remain unchanged.
- Reversal creation must be persisted before the proposed in-memory state is committed.

### BR-23: Reversal Reporting and Historical Integrity

- The original transaction must remain visible in historical transaction records.
- The reversal must appear as a separate historical record.
- The relationship between an original transaction and its reversal must be maintained through `reverses_transaction_id`.
- Reversed original DEPOSIT and WITHDRAW transactions must be excluded from effective income and expense reporting.
- REVERSAL transactions must not independently contribute to ordinary income and expense totals.
- The replacement transaction recorded by the user must be treated as a normal independent transaction.
- Reversal records must remain available in transaction history.
- Reversal operations must comply with the transaction ceiling established in BR-09.

## 2.7 Transaction History Pagination

### BR-24: Transaction Pagination

- The system must support application-level pagination when retrieving transaction history.
- The default transaction page size must be 25 records.
- Users must be able to navigate between available transaction history pages through the CLI.
- Pagination must not modify or remove historical transaction records.
- Transactions must be sorted in reverse-chronological order by default.
- Pagination must be applied after the relevant filtering and sorting operations.
- The system must handle empty pages and out-of-range page requests gracefully.

## 2.8 Transaction Searching and Filtering

### BR-25: Compound Transaction Filtering

- The system must support searching and filtering historical transaction records using multiple criteria.
- Supported filtering criteria must include:
  - Transaction date.
  - Inclusive transaction date ranges.
  - Transaction classification.
  - Expense category.
  - Associated account.
  - Minimum transaction amount.
  - Maximum transaction amount.
- Multiple active filters must be evaluated together using logical AND conditions.
- Account-based filtering must consider both source and target account references.
- REVERSAL transactions must be identifiable through transaction-type filtering.
- Original transaction references must be available for identifying reversal relationships.
- Filtering must not modify the historical transaction collection.

### BR-26: Empty Search Results

- When a search or compound filter produces no matching transactions, the Business Logic Layer must return an empty collection.
- An empty search result must not raise an exception.
- The presentation layer must display a clear notification indicating that no matching transactions were found.
- The CLI must provide an option to reset active filters and return to unfiltered transaction history.

## 2.9 Financial Reporting and Aggregate Balances

### BR-27: Date-Bounded Financial Reporting

- The system must support financial reporting within a user-selected start date and end date.
- Both reporting dates must be inclusive.
- The start date must not be later than the end date.
- Reporting dates must comply with the application's date validation rules.
- Only transactions falling within the selected reporting period must contribute to the report.
- Reporting must operate on effective transactions where ordinary income and expense calculations are concerned.

### BR-28: Core Financial Reporting Metrics

For the selected reporting period, the system must calculate:

- **Total Income:** Sum of effective DEPOSIT transactions.
- **Total Expenses:** Sum of effective WITHDRAW transactions.
- **Net Delta:** Total Income minus Total Expenses.

Additional rules:

- TRANSFER transactions must be excluded from ordinary income and expense totals.
- Reversed original DEPOSIT and WITHDRAW transactions must be excluded from effective reporting calculations.
- REVERSAL transactions must not independently contribute to ordinary income or expense totals.
- All calculations must use integer Kobo.

### BR-29: Expense Category Breakdown

- The reporting engine must provide a breakdown of expenditure grouped by expense category.
- Only effective WITHDRAW transactions must contribute to expense-category totals.
- Transactions must be grouped according to their recorded expense categories.
- Each category total must represent the sum of all qualifying transactions within the selected reporting period.
- Reversed original expense transactions must not contribute to category totals.
- All category totals must be expressed in integer Kobo internally.

### BR-30: Aggregate Net-Worth Calculation

- The system must calculate the aggregate net balance across all ACTIVE accounts.
- The aggregate net balance must be calculated by summing the ledger-derived balances of individual active accounts.
- Inactive accounts must be excluded from the active-account aggregate dashboard.
- The aggregate calculation must not count internal transfers as additional income or expenditure.
- The aggregate balance must remain consistent with the individual ledger-derived account balances.
- The dashboard must present the aggregate balance in Nigerian Naira with two decimal places.

### BR-31: Per-Account Financial Activity Reporting

- The system must provide financial activity summaries for individual accounts.
- Account-level reporting must identify financial movements within a selected reporting period.
- The report must distinguish between incoming and outgoing financial activity.
- DEPOSIT transactions must be classified as incoming account activity.
- WITHDRAW transactions must be classified as outgoing account activity.
- TRANSFER transactions must be represented as outgoing activity for the source account and incoming activity for the target account.
- REVERSAL transactions must reflect the inverse financial movement of their original transactions.
- Reversed original transactions must not be counted independently alongside their corresponding reversal when calculating effective financial activity.
- Account-level reporting must preserve the distinction between historical transactions and their effective financial effects.

## 2.10 Persistence and Data Integrity

### BR-32: Atomic State Persistence

- All successful account and financial transaction operations must be persisted through the established storage mechanism.
- Proposed application state must be prepared independently before committing changes to the active in-memory state.
- The application must persist proposed state before replacing its current in-memory state.
- If persistence fails, the current in-memory state must remain unchanged.
- Account creation, account deactivation, account reactivation, deposits, withdrawals, transfers, and reversals must follow this persistence sequence.
- Financial operations affecting multiple accounts must be committed as one logical operation.
- The persistence mechanism must use the established staging-file and atomic replacement strategy.

### BR-33: Persisted Data Validation

- Persisted application data must undergo business validation when loaded.
- Transaction identifiers must be unique.
- Reversal references must point to existing historical transactions.
- A reversal must not reference another reversal.
- An original transaction must not have multiple reversal records.
- Reversal amounts and account references must match those of their original transactions.
- Transaction account references must point to existing accounts.
- Historical transaction data must satisfy chronological balance consistency.
- Persisted data that fails business validation must be treated as corrupted application data.
- Corrupted persisted data must raise `StorageCorruptedError`.

# 3\. Assumptions

## ASM-01: Single-User Execution Environment

- The system assumes an isolated, local execution architecture dedicated to a single user profile.
- Multiple user profiles, remote user authentication, role-based access controls (RBAC), and session management are outside the current design scope.
- All account and transaction records are assumed to belong to the single configured user profile.

## ASM-02: Ex Post Facto Ledger Recording

- All manually entered financial records are assumed to represent transactions that have already occurred in the real world.
- Users are responsible for entering transaction information that accurately reflects completed financial activities.
- This assumption justifies the rejection of future-dated transactions.
- The application is not intended to execute or schedule future financial transactions.

## ASM-03: Single-Threaded Execution and File Access

- The system assumes synchronous, single-threaded execution by one application process at a time.
- Concurrent application instances accessing the same persistence file are outside the supported execution model.
- Multi-process write conflicts, concurrent modification, and race-condition prevention are not guaranteed.
- The application assumes exclusive write access to its persistence file during normal execution.

## ASM-04: Environment and Runtime Compatibility

- The application assumes execution within a standard command-line interface terminal.
- Python 3.11 or later must be installed on the host operating system.
- The host environment must provide filesystem access for reading and writing application data.
- The application assumes that the host filesystem supports the atomic file-replacement operation required by the persistence mechanism.

## ASM-05: Controllable System Date Provider

- The application must obtain the current calendar date through a dedicated date-provider function rather than directly accessing the system clock throughout the Business Logic Layer.
- During normal execution, the provider must return the host operating system's current local calendar date.
- The date provider must be replaceable or injectable during automated testing.
- All future-date validation and date-dependent business operations must use the date returned by this provider.
- The application assumes that the host operating system's configured date is reasonably accurate.

## ASM-06: Controlled Application Configuration

- The application assumes that supported account types, transaction classifications, and expense categories are centrally defined.
- Configuration changes must be made through controlled application updates rather than arbitrary user modifications to the JSON persistence file.
- Historical transaction records must remain readable following compatible configuration updates.
- The application assumes that supported configuration values remain consistent with the validation rules enforced by the Business Logic Layer.

## ASM-07: Local Persistence Availability

- The application assumes that its configured data directory is accessible during normal execution.
- The application assumes sufficient filesystem permissions and available storage capacity for persistence operations.
- The persistence mechanism is responsible for detecting and reporting unsuccessful file operations.
- Users are responsible for maintaining appropriate backups of their persisted application data.
- The application does not guarantee recovery from physical storage failure, filesystem corruption, or external deletion of persisted data.

# 4\. Identified Ambiguities

## AMB-01: Terminal Interaction Pattern

- **Ambiguity:** The original requirements define functional capabilities but do not specify how users should interact with the application through the CLI.
- **Resolution:** The application will use a synchronous interactive menu loop implemented with Python's native `input()` utility rather than raw command-line argument parsing.
- Menu navigation will be managed through predefined application states.
- User selections will determine the operations dispatched by the application.

## AMB-02: Structural Casing for Account-Name Uniqueness

- **Ambiguity:** The original requirements require unique account names but do not define how capitalization and whitespace should affect uniqueness.
- **Resolution:** Account-name uniqueness will be evaluated case-insensitively across existing accounts.
- Leading and trailing whitespace will be removed before validation and persistence.
- **Example:** "Cash" and "cash" will be treated as duplicate account names.
- Account names must not be empty or consist exclusively of whitespace.
- No maximum account-name length is imposed.
- Account-name uniqueness validation will apply during account creation and account renaming.
- Reactivation will not perform an account-name uniqueness check.

## AMB-03: Persistence Technology Selection

- **Ambiguity:** The original requirements specify persistent transaction history but do not prescribe a storage technology.
- **Resolution:** The application will use a structured JSON flat file as its exclusive persistence mechanism.
- SQLite and other database management systems are excluded from the current implementation.

**Justification:**

JSON provides a lightweight, human-readable persistence mechanism suitable for the application's single-user, single-process execution environment. It integrates directly with Python's native `json` module and supports the established Data Access Layer architecture.

**Trade-off:**

JSON does not provide native database indexing, query optimization, transactional rollback, or database-level concurrency controls. Consequently, large transaction histories will increase file parsing, serialization, filtering, and pagination costs.

## AMB-04: Transaction Category and Description Semantics

- **Ambiguity:** The requirements distinguish descriptive labels from expense categories but do not explicitly define how these fields apply to each transaction type.
- **Resolution:**
  - WITHDRAW transactions must contain a valid expense category and may contain a descriptive label.
  - DEPOSIT transactions may contain a descriptive label but do not require an expense category.
  - TRANSFER transactions may contain a descriptive label but do not require an expense category.
  - REVERSAL transactions must inherit their financial references from the original transaction and may contain a descriptive correction label.
- The category field must be `null` for DEPOSIT, TRANSFER, and REVERSAL records.
- The category field must not be used to classify transfers or reversals.

## AMB-05: Account Balance Initialization

- **Ambiguity:** The original requirements do not define how newly created accounts acquire their initial balances.
- **Resolution:** All newly created accounts must begin with zero Kobo.
- Initial funding must be recorded through a valid DEPOSIT transaction rather than directly assigning a starting balance.
- This preserves the transaction ledger as the authoritative source of account balances.

## AMB-06: Transaction Correction Mechanism

- **Ambiguity:** The original requirements establish an immutable transaction ledger but do not specify how users recover from incorrectly recorded transactions.
- **Resolution:** Historical transactions must never be directly edited or deleted through normal application operations.
- Incorrect transactions must be corrected through compensating REVERSAL transactions.
- The user may subsequently record a replacement transaction containing the correct information.
- Original transactions and their corresponding reversals must remain independently identifiable in the historical ledger.
- A transaction may only be reversed once.

## AMB-07: Architecture Dependency Direction

- **Ambiguity:** The original architecture describes communication between the Business Logic and Data Access Layers without defining dependency ownership.
- **Resolution:** The application will use one-way runtime interaction:
  - Presentation Layer calls the Business Logic Layer.
  - Business Logic Layer interacts with an abstract storage interface.
  - Data Access Layer implements that interface.
  - The application entry point connects the concrete storage implementation to the Business Logic Layer.
- The Data Access Layer must not import or depend on the Business Logic Layer or Presentation Layer.
- Dependency injection will allow business operations to be tested without requiring physical disk access.

# 5\. Architecture and Layout Blueprint

## 5.1 Three-Tier Layer Separation

### 5.1.1 Presentation Layer (`ui/`)

- Manages terminal rendering and command-line display.
- Collects synchronous string inputs using Python's native `input()` utility.
- Displays validation errors, transaction confirmations, account information, and financial reports.
- Invokes application operations through the Business Logic Layer.
- Must not execute financial calculations or access JSON storage files directly.
- Must not contain independent implementations of business validation rules.
- Must catch expected application exceptions at appropriate user-operation boundaries.

### 5.1.2 Business Logic Layer (`models/` and `services/`)

- Implements business workflows and domain validation.
- Evaluates account, transaction, monetary, category, and date constraints.
- Coordinates account creation, renaming, deactivation, and reactivation.
- Coordinates income, expense, transfer, and reversal operations.
- Calculates ledger-derived account balances.
- Implements transaction searching, filtering, sorting, and pagination.
- Implements date-bounded financial reporting and account-level activity reports.
- Calculates aggregate net worth across active accounts.
- Manages proposed in-memory state changes before persistence.
- Depends on an abstract storage contract rather than a concrete JSON implementation.
- Must not perform direct filesystem operations.

**Domain entities:**

- `Account` represents a financial account, including its identity, name, account type, creation timestamp, and status.
- `Transaction` represents an immutable financial event, including its identity, classification, amount, account references, date, and optional metadata.

These entities represent application data and domain concepts. They are not merely collections of validators.

Validation rules may be implemented through entity methods, dedicated validation functions, or application services depending on their scope.

### 5.1.3 Data Access Layer (`file_manager/`)

- Isolates all disk input/output operations.
- Implements the abstract storage interface defined by the Business Logic Layer.
- Handles JSON deserialization and serialization.
- Executes staging-file writes and atomic replacement.
- Validates the structural integrity of loaded persistence data.
- Translates filesystem and serialization failures into controlled persistence exceptions.
- Must not import or depend on Business Logic or Presentation modules.

### 5.1.4 Dependency Direction

The logical dependency direction is:

text

```text
                 USER
                  |
                  v
          PRESENTATION LAYER
                 (ui/)
                  |
                  v
          BUSINESS LOGIC LAYER
          (models/ and services/)
                  |
                  v
           STORAGE INTERFACE
          (storage_interface.py)
                  ^
                  |
           DATA ACCESS LAYER
              (storage.py)
                  |
                  v
           LOCAL JSON STORAGE
```

The concrete storage implementation is injected into the Business Logic Layer during application initialization.

The application entry point (`main.py`) acts as the composition root responsible for connecting the required components.

**Dependency constraints:**

- The Presentation Layer may import and call Business Logic operations.
- The Business Logic Layer may depend on the abstract storage interface.
- The Data Access Layer implements the storage interface without importing the Business Logic Layer.
- `main.py` imports and initializes the concrete application components.
- The Data Access Layer must never call Business Logic operations directly.
- No layer may bypass the established dependency boundaries to access another layer's internal implementation details.

# 6\. Persistence Architecture and Integrity Guard

## 6.1 Serialization Lifecycle (`json.dump()` / `json.load()`)

### 6.1.1 Data Extraction (Deserialization)

- Upon application startup, the Data Access Layer must use Python's native `json.load()` function to read the local storage file.
- The raw JSON payload must be parsed into native Python dictionaries and lists.
- The loaded data must be validated against the expected storage structure before being exposed to the Business Logic Layer.
- Valid records must be reconstructed into their corresponding domain entities through their respective deserialization methods.
- Integer monetary values must remain integers after deserialization.
- Binary floating-point monetary values must be rejected.
- Invalid persisted account statuses, transaction classifications, identifiers, monetary values, account references, or reversal relationships must trigger controlled data-integrity failures.
- Missing required attributes and structurally invalid JSON records must be treated as corrupted persisted data.
- A missing storage file must be treated as a new application installation, initializing empty account and transaction collections.

### 6.1.2 Data Serialization

- When application state changes, the Data Access Layer must serialize the complete proposed application state using Python's native `json.dump()` method.
- JSON serialization must use a consistent indentation format to preserve human readability.
- Monetary values must be serialized as JSON integers rather than floating-point numbers.
- Account serialization must be delegated to the Account domain model.
- Transaction serialization must be delegated to the Transaction domain model.
- Historical transactions must retain their original identifiers and immutable attributes during serialization.
- Account identifiers must remain consistent between JSON object keys and their corresponding serialized account identifiers.
- Transaction references must remain valid and unchanged during serialization.

## 6.2 Atomic Write Fail-Safe Strategy

- The application must never write directly into the active JSON storage file during normal state updates.
- Instead, the complete proposed application state must first be written into a temporary staging file named `.storage.json.tmp`.
- The staging file must be created in the same directory as the destination `storage.json` file.
- The Data Access Layer must serialize the complete proposed state before attempting to replace the existing storage file.
- After successful serialization, the serialized contents must be written to the staging file.
- The staging file must be flushed before replacement.
- The Data Access Layer must execute `os.replace()` to atomically replace the active storage file.
- The replacement operation must occur only after successful serialization and staging-file writing.
- The temporary staging file must not be treated as an alternative authoritative storage location.

### Atomic Replacement Guarantees

- Both files must reside on the same filesystem.
- Readers will observe either the previous complete JSON file or the newly replaced JSON file, subject to the supported filesystem's atomic replacement guarantees.
- The destination file must not be exposed as a partially serialized JSON document during a successful atomic replacement.
- A successful replacement must make the complete proposed application state available as the active persisted state.

### Durability Considerations

- Atomic replacement alone does not guarantee complete durability against every possible operating-system crash or power failure.
- The application should flush and synchronize staging-file contents using `flush()` and `os.fsync()` before replacement.
- Where supported, the containing directory should also be synchronized after replacement to strengthen directory-entry durability.
- These additional synchronization measures improve crash durability but do not guarantee protection against every hardware or filesystem failure.

## 6.3 In-Memory State Consistency and Transaction Commit

- The system must never mutate the active in-memory application state before successfully persisting the corresponding changes to disk.
- Before executing a financial transaction, the Business Logic Layer must create an independent proposed copy of the current application state.
- Proposed account balance mutations and transaction ledger additions must be applied exclusively to this proposed state.
- For operations involving multiple accounts, all affected account changes must be applied to the same proposed state.
- The Data Access Layer must serialize and persist the complete proposed state using the staging-file and atomic replacement strategy.
- Only after successful completion of the file replacement operation may the Business Logic Layer commit the proposed state as the new active in-memory application state.
- The committed in-memory state must represent the same logical application state as the successfully persisted JSON document.

### Persistence Failure Handling

If persistence fails at any stage before successful replacement:

- The proposed state must be discarded.
- The original in-memory state must remain unchanged.
- The previously persisted JSON state must remain unchanged.
- Any incomplete staging file must be removed where possible.
- A `DatabaseWriteException` must be raised.
- The UI must report the failure without displaying a transaction success confirmation.

If replacement succeeds:

- The newly persisted JSON document becomes the authoritative stored state.
- The corresponding proposed state must be committed to active memory.
- The application must not attempt to roll back an already successful replacement merely because a later operation encounters an error.

This process ensures that the application does not expose an unpersisted financial transaction as a successful operation.

## 6.4 Transaction Guarantee and Failure Boundaries

The application implements a single-file transactional persistence strategy rather than a full database transaction mechanism.

The logical transaction consists of proposed account balance mutations and corresponding ledger additions, persisted together through one complete JSON state replacement.

### The System Guarantees That:

- The active in-memory application state remains unchanged until successful file replacement.
- The existing JSON file remains intact if serialization or staging-file writing fails before replacement.
- A successful replacement makes the complete new JSON state visible as the active persisted state.
- A failed replacement prevents the proposed in-memory state from being committed.
- Account balance mutations and transaction ledger additions are committed together.
- Income and expense operations persist their corresponding ledger records and financial effects together.
- Transfers affecting two accounts are persisted as one complete state update.
- Reversals affecting one or multiple accounts are persisted as one complete state update.
- Account activation and deactivation changes are persisted using the same atomic replacement mechanism.

### The System Does Not Guarantee:

- Database-level transaction isolation.
- Multi-process concurrency control.
- Protection against every possible hardware failure.
- Guaranteed recovery from every operating-system crash.
- Automatic rollback after a replacement that has already succeeded.
- Database-level indexing or optimized query execution.

These capabilities are outside the current single-process JSON persistence architecture.

## 6.5 Persistence Scalability Constraints

- The application will use one structured JSON file as its exclusive persistence mechanism.
- The system is designed for a single-user, single-process environment with moderate transaction volumes.
- The accepted operational capacity for the current release is up to **10,000 historical transaction records**.
- The transaction capacity must account for every transaction classification, including INCOME, EXPENSE, TRANSFER, and REVERSAL.
- Transaction retrieval, searching, compound filtering, sorting, and pagination will be performed in application memory after loading the JSON dataset.
- Pagination will limit the number of records returned to the presentation layer but will not eliminate the computational cost of loading and processing the underlying transaction collection.
- The application must monitor the number of historical transaction records stored in the JSON ledger.

### 6.5.1 Capacity Warning

- When the transaction count reaches 9,000 records, the system must display a capacity warning informing the user that the application is approaching its supported transaction limit.
- The warning must not interfere with otherwise valid financial operations.
- The warning must remain applicable until the transaction count falls below the warning threshold, if transaction removal is ever introduced through an authorized maintenance or migration process.

### 6.5.2 Maximum Capacity Enforcement

- The application must enforce a maximum capacity of 10,000 historical transaction records.
- Once the ledger reaches 10,000 records, the system must reject any new INCOME, EXPENSE, TRANSFER, or REVERSAL operation that would increase the count beyond the supported limit.
- Capacity validation must occur before proposed account balance mutations, ledger modifications, or persistence operations.
- The capacity check must be performed by the Business Logic Layer.
- Existing in-memory and persisted states must remain unchanged following capacity rejection.
- The user must receive a clear notification explaining that transaction capacity has been reached and that a persistence architecture reassessment is required.
- Rejected operations must not generate transaction identifiers that are subsequently treated as committed transaction records.

### 6.5.3 Future Migration Path

- Transaction volumes exceeding the supported capacity will require an explicit architecture reassessment.
- SQLite is identified as the preferred migration path because it provides:
  - Structured queries.
  - Database indexing.
  - Transactional capabilities.
  - More efficient retrieval of large transaction histories.
  - Better scalability for compound filtering and reporting operations.
- Migration must preserve existing account identifiers, transaction identifiers, historical records, reversal relationships, and financial integrity.
- The JSON persistence implementation must remain isolated behind the storage interface to minimize the impact of a future storage-engine replacement.
