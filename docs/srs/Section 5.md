# 5\. Architecture and Layout Blueprint

## 5.1 Three-Tier Layer Separation

### Presentation Layer (`ui/`)

- Manages terminal rendering and command-line display.
- Collects synchronous string inputs using Python's `input()` utility.
- Displays validation errors, transaction confirmations, account information, and reports.
- Invokes application operations through `services/`.
- Must not execute financial calculations or access JSON storage files directly.
- Must not contain independent implementations of business validation rules.
- Must catch expected application exceptions at appropriate user-operation boundaries.

### Core Domain Layer (`models/` and `exceptions/`)

- Has no dependencies on the Presentation, Business Logic, or Data Access Layers.
- Defines domain entities (`Account`, `Transaction`), enums, and custom application errors.
- `Account` represents a financial account, including its identity, name, account type, creation timestamp, and status.
- Account entities must not contain independently stored or cached balance attributes.
- Account identifiers must be generated by the Business Logic Layer and supplied during account construction.
- `Transaction` represents an immutable financial event, including its identity, classification, amount, account references, date, and optional metadata.
- Supported transaction classifications are `INCOME`, `EXPENSE`, and `TRANSFER`.
- Entities represent core domain concepts and enforce their own single-record field invariants, including `from_dict()` and `to_dict()` serialization.
- Cross-entity business rules must be enforced within `services/`.

### Business Logic Layer (`services/`)

- Implements business workflows and cross-entity domain validation (`_validate_loaded_data()` and `_validate_chronological_balances()`).
- Enforces the chronological balance invariant through `_validate_chronological_balances()`.
- Evaluates account, transaction, monetary, category, and date constraints.
- Coordinates account creation, renaming, deactivation, and reactivation.
- Generates unique account identifiers at the service layer and performs duplicate checks before account creation.
- Coordinates income, expense, and transfer operations.
- Supports transaction correction through ordinary compensating transactions.
- Calculates ledger-derived account balances without relying on stored account balance attributes.
- Implements transaction searching, filtering, sorting, pagination, and financial reporting.
- Manages proposed in-memory state changes before persistence.
- Must not perform direct filesystem operations.

### Data Access Layer (`file_manager/`)

- Isolates all disk input/output operations.
- Handles JSON deserialization and serialization (`load_app_data()` and save operations).
- Executes staging-file writes (`.storage.json.tmp` with `flush()` and `os.fsync()`) and atomic replacement (`os.replace()`).
- Validates the structural integrity of loaded JSON data and delegates record reconstruction to `models/` through `from_dict()`.
- Translates filesystem, serialization, and read-side integrity failures into controlled persistence exceptions (`StorageReadError` and `StorageWriteError` defined in `exceptions/`).
- Must not import or depend on `services/` or `ui/`.
- Must depend only on the domain models and application exceptions.

### Dependency Direction

The logical dependency direction is:

text

```text
                  USER
                   |
                   v
           PRESENTATION LAYER
                 (ui/)
                   |
                   v
           BUSINESS LOGIC LAYER
               (services/)
                   |
                   v
           DATA ACCESS LAYER
              (file_manager/)
                   |
                   v
            LOCAL JSON STORAGE


       +------------------------------+
       |       DOMAIN & ERRORS        |
       |                              |
       |       models/                |
       |       exceptions/            |
       +------------------------------+

       Domain components may be imported
       by all application layers.

       main.py acts as the composition root
       and connects the concrete components.
```

**Dependency constraints:**

- `models/` and `exceptions/` form the dependency-free Domain base and must not depend on outer application layers.
- `ui/` may import and call `services/` but must never access `file_manager/` directly.
- `services/` imports and calls the concrete persistence functions in file_manager/storage.py.
- `file_manager/`  handles JSON loading, serialization, and file persistence.
- `file_manager/` must not import or depend on services/ or ui/.
- `main.py` initializes the application components.
- No layer may bypass these boundaries to access another layer's internal implementation details.

**Module responsibilities:**

- `account.py`: Defines the Account entity and account-specific structural invariants. It accepts an externally generated identifier supplied by the service layer.
- `transaction.py`: Defines the immutable Transaction entity and transaction-specific structural invariants.
- `enums.py`: Defines supported account statuses, account types, and transaction classifications.
- `wallet_engine.py`: Coordinates application workflows, account ID generation, cross-entity validation, chronological balance validation, and state transitions.
- `reporting.py`: Calculates financial summaries and account activity reports using ledger-derived values.
- `query_service.py`: Implements transaction retrieval, filtering, sorting, and pagination.
- `storage.py`: Implements JSON loading, deserialization, serialization, and atomic file replacement.
- `errors.py`: Defines the common application exception hierarchy.
- `validators.py`: Implements reusable monetary and date validators.
- `constants.py`: Stores centrally defined expense categories and application constants.
- `logger.py`: Configures application logging.
- `date_provider.py`: Provides an injectable source of the current calendar date.

## 5.3 Domain Entity Design

### Account Entity

The Account entity must represent a financial account and enforce its structural requirements.

Its properties include:

- `id`: Unique account identifier generated by the service layer.
- `acc_name`: Validated account name.
- `acc_type`: Supported account type.
- `status`: ACTIVE or INACTIVE.
- `created_at`: Automatically generated creation timestamp.

Account construction must accept an identifier generated by the Business Logic Layer.

The Account entity must not generate its own identifier or maintain an account balance attribute.

The service layer is responsible for generating account identifiers and checking them against existing account identifiers before constructing the entity.

**Illustrative construction:**

python

```python
account = Account(
    id=generated_account_id,
    name="First Bank",
    account_type=AccountType.BANK
)
```

The entity must internally assign its creation timestamp and initial ACTIVE status.

Account balances must be calculated dynamically from associated transaction records rather than maintained as account properties.

### Transaction Entity

The Transaction entity must represent an immutable historical financial event.

Its properties include:

- `id`: Unique transaction identifier.
- `amount`: Positive integer Kobo value.
- `trx_type`: INCOME, EXPENSE, or TRANSFER.
- `category`: Optional expense category, mandatory for EXPENSE transactions.
- `desc`: Optional descriptive label.
- `source_acc_id`: Source account reference where applicable.
- `target_acc_id`: Target account reference where applicable.
- `transaction_date`: Validated calendar date.

The transaction entity must not permit direct mutation of historical transaction attributes after creation.

Transaction classification must strictly follow these rules:

- **INCOME:** Must reference a target account and must have a null source account.
- **EXPENSE:** Must reference a source account and must have a null target account.
- **TRANSFER:** Must reference both a source account and a target account, which must be distinct.

Category constraints:

- EXPENSE transactions must contain a valid expense category.
- INCOME and TRANSFER transactions must have `category = None`.

Transaction corrections must be represented through new ordinary transactions rather than dedicated REVERSAL records.

Counteracting transactions must retain the appropriate ordinary transaction classification and use their descriptive label to provide correction context.

The Transaction entity must not contain a `reverses_transaction_id` attribute or any special reversal relationship.

## 5.4 Data Structure

The application must persist account and transaction records using a structured JSON document.

**Illustrative JSON structure:**

json

```json
{
  "accounts": {
    "acc_aBc12": {
      "id": "acc_aBc12",
      "acc_name": "First Bank",
      "acc_type": "BANK",
      "status": "ACTIVE",
      "created_at": "2026-11-10T09:30:00"
    },
    "acc_cBg5i": {
      "id": "acc_cBg5i",
      "acc_name": "Savings Acc",
      "acc_type": "SAVINGS",
      "status": "ACTIVE",
      "created_at": "2026-11-10T10:00:00"
    }
  },
  "transactions": [
    {
      "id": "trx_105Df",
      "amount": 1050000,
      "trx_type": "INCOME",
      "category": null,
      "desc": "Initial account funding",
      "source_acc_id": null,
      "target_acc_id": "acc_aBc12",
      "transaction_date": "2026-11-10"
    },
    {
      "id": "trx_123Df",
      "amount": 25000,
      "trx_type": "EXPENSE",
      "category": "food",
      "desc": "Groceries",
      "source_acc_id": "acc_aBc12",
      "target_acc_id": null,
      "transaction_date": "2026-11-10"
    },
    {
      "id": "trx_1oerf",
      "amount": 500000,
      "trx_type": "TRANSFER",
      "category": null,
      "desc": "Moving to savings",
      "source_acc_id": "acc_aBc12",
      "target_acc_id": "acc_cBg5i",
      "transaction_date": "2026-11-10"
    },
    {
      "id": "trx_8kLm2",
      "amount": 500000,
      "trx_type": "TRANSFER",
      "category": null,
      "desc": "Correction of incorrectly recorded transfer",
      "source_acc_id": "acc_cBg5i",
      "target_acc_id": "acc_aBc12",
      "transaction_date": "2026-11-11"
    }
  ]
}
```

**Data structure constraints:**

- Account IDs must be unique.
- Account IDs must be generated at the service layer, with duplicate checks performed before account creation.
- Transaction IDs must be unique.
- Account records must not contain stored or cached balance attributes.
- Transaction amounts must be stored as positive integer Kobo values.
- Account statuses must be either ACTIVE or INACTIVE.
- Account creation timestamps must use a consistent ISO 8601 datetime representation.
- Transaction dates must use YYYY-MM-DD.
- INCOME records must have a target account and a null source account.
- EXPENSE records must have a source account and a null target account.
- TRANSFER records must have both source and target accounts.
- TRANSFER source and target accounts must be distinct.
- Only EXPENSE records require a non-null category.
- INCOME and TRANSFER records must have null categories.
- Expense categories must belong to the centrally defined expense-category collection.
- A transaction must not reference an account that did not exist when the transaction was originally recorded.
- Historical transaction identifiers, account references, and financial attributes must remain unchanged.
- Counteracting transactions must be stored as independent ordinary transactions.
- The JSON structure must not contain dedicated REVERSAL classifications or reversal-reference fields.
- Account balances must be derived from the transaction ledger rather than persisted as account attributes.

The JSON structure is illustrative. Actual account and transaction identifiers must be generated dynamically rather than copied from the example.
